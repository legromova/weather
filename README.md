# Погодный AI-помощник

Локальный русскоязычный чат: **пользователь → AI-агент OpenAI → клиент MCP → готовый удалённый MCP-сервер → Open-Meteo → ответ**.

Собственный MCP-сервер не создаётся и не запускается. Локальный Express — обычная серверная часть приложения, которая хранит API-ключ, историю и выполняет MCP-клиент. Погодных HTTP-запросов напрямую к Open-Meteo в приложении нет. Платный ключ погоды не нужен; OpenAI API требует собственного доступа и может тарифицироваться отдельно.

**Статус: живая MCP-интеграция и основной диалог с настоящей моделью OpenAI проверены.** 22.11.2026 модель `gpt-5.4-mini` самостоятельно получила погоду Екатеринбурга, сменила город на Казань в Татарстане и выполнила новые погодные вызовы для вопросов «А завтра?» и о ветре. Проверки SDK и моки отдельно обозначены в отчётах.

## Запуск на Windows

Требуется Node.js 24 LTS или новее, npm и интернет.

В PowerShell в каталоге проекта:

```powershell
npm ci
Copy-Item .env.example .env
notepad .env
```

Заполните **локально**, не публикуя ключ:

```dotenv
OPENAI_API_KEY=ваш_ключ_OpenAI
OPENAI_MODEL=имя_доступной_вам_модели
MCP_SERVER_URL=https://weather.chukai.io/mcp
PORT=3001
```

Выберите в своём аккаунте OpenAI модель с поддержкой function calling в Chat Completions. Приложение передаёт ей схемы инструментов с `strict: false` и отключёнными параллельными вызовами. Доступ к модели зависит от аккаунта; наличие подписки на чат само по себе не подтверждает доступ к API. Имя модели меняется в `.env`, исходники менять не требуется. Формат вызовов: [официальная документация OpenAI](https://developers.openai.com/api/docs/guides/function-calling).

```powershell
npm run dev
```

Откройте **http://127.0.0.1:5173/**. Интерфейс и API (порт 3001 по умолчанию) привязаны к `127.0.0.1`. Остановить оба процесса — `Ctrl+C`. После изменения `.env` перезапустите команду. При занятом порте интерфейса Vite напечатает фактический адрес. Изменение `PORT` применяется также к прокси интерфейса.

Проверка готовой сборки:

```powershell
npm run build
npm start
```

После сборки Express раздаёт интерфейс на **http://127.0.0.1:3001/** (или настроенном `PORT`).

Команды `dev`, `start`, `probe:mcp` и `verify:live` запускают Node.js с `--use-system-ca`: доверенные сертификаты ОС дополняют встроенное хранилище Node.js. Это необходимо, например, если HTTPS проверяется локальным антивирусом или корпоративным прокси с сертификатом, уже доверенным Windows. Проверка TLS остаётся включённой; не задавайте `NODE_TLS_REJECT_UNAUTHORIZED=0`. См. [документацию Node.js](https://nodejs.org/api/cli.html#--use-system-ca).

При ошибке OpenAI сервер записывает безопасные диагностические поля: HTTP-статус, код, параметр, идентификатор запроса провайдера и коды цепочки причин, без исходного текста исключения и ключа. Интерфейс различает ошибки сертификата, сети, доступа к модели и параметров запроса.

## Как устроен агент

1. Браузер создаёт случайную сессию локального API. История сообщений и подтверждённые геоданные остаются в памяти сервера.
2. Сервер подключает официальный MCP SDK через Streamable HTTP и получает все страницы `tools/list` с фактическими JSON-схемами.
3. Модели передаются исходные описания и схемы одиночных инструментов, системные правила, история и сообщение. Модель сама решает, уточнять город, искать координаты, получать текущие условия или прогноз. Обработчика погодных ключевых слов нет.
4. Аргументы выбранного инструмента проверяет Ajv. Координаты погодного запроса должны точно совпадать с ранее полученными через MCP геоданными. Выдуманные координаты отклоняются до сетевого вызова.
5. Выполнитель делает настоящий `tools/call`, записывает начало/итог в журнал и серверную консоль с requestId и передаёт данные модели. `isError`, пустой JSON и отсутствие пригодных показателей не считаются погодой.
6. Программная нормализация сохраняет нули, различает отсутствующие значения, переводит ветер в м/с и расшифровывает WMO-коды по [документации Open-Meteo](https://open-meteo.com/en/docs). Модель получает и исходные данные, и нормализованные показатели.
7. Ответ возвращается по-русски. Браузер получает отдельные реальные события этапов и MCP-вызовов через NDJSON, а не выдуманный моделью журнал.

До 8 фактических инструментальных попыток, включая единственный повтор при временном сетевом сбое, на сообщение; общий предел — 90 секунд. Дополнительно ограничены шаги модели, длина сообщения и объём чата. Обрыв браузерного соединения отменяет запрос. Кнопка «Новый чат» удаляет предыдущую серверную сессию и очищает экран; перезагрузка страницы создаёт новый контекст. Неактивные сессии удаляются через час.

Модель получает местное время и IANA-пояс из реальных геоданных. Для «завтра» требуется прогноз минимум на два дня, для вечера — почасовые данные 18:00–23:00 нужного местного дня. Если пояс/интервал не установлен, инструкция требует уточнения. Прогноз отличается от текущей погоды, вероятность осадков — от утверждения о дожде.

В журнале под ответом: имя инструмента, связанный город, точные аргументы (включая координаты), состояние, начало и длительность, исходный результат или ошибка. Погодное время находится в ответе; время получения ответа показано отдельно с часовым поясом браузера.

Моки SDK используются только в изолированных тестах; собственный MCP-сервер не создаётся.
- `npm run build`: TypeScript и production-сборка прошли.
- `npm audit`: 0 известных уязвимостей на момент проверки. Точные прямые версии указаны в package.json; транзитивные зафиксированы в package-lock.json.
- `npm run probe:mcp`: реальная протокольная проверка, сохраняет сырые ответы и схемы. Это диагностический MCP-клиент, а не MCP-сервер.
- `npm run verify:live`: реальная интеграция через тот же WeatherMcp, что использует приложение; Екатеринбург → Казань с новыми вызовами, прогноз и обработка неслушающего адреса `127.0.0.1:1` (сервер на нём не запускается). Если настройки OpenAI присутствуют, дополнительно проверяет настоящий диалог: Екатеринбург → Казань в Татарстане → завтра → ветер. Без ключа проверка модели явно помечается NOT VERIFIED.
- После исправления доверия к системным сертификатам полный запуск `verify:live` с настроенным аккаунтом завершился с `agent: passed`. Отчёт: `diagnostics/live-verification.json`. Модель подтвердила доступ коротким запросом; исходная ошибка HTTPS не была ошибкой имени модели или ключа.
- Браузер: интерфейс отрисовался на узком экране; кнопка примера прошла через браузер → Vite proxy → API → понятное сообщение о ненастроенной модели. «Новый чат» очистил сообщения. Макет сохранён в `diagnostics/interface.jpg`.
- После настройки ключа и исправления TLS приложение перезапущено. Повторная браузерная проверка получила настоящий ответ о погоде Екатеринбурга и два успешных MCP-вызова (`geocode_location`, `get_weather_forecast`). Подтверждение: `diagnostics/openai-fixed.jpg`.

После настройки ключа обязательна ручная проверка полного пользовательского сценария: спросить про Екатеринбург, сменить город на Казань (при уточнении выбрать Татарстан), спросить «А завтра?» и «А какой там ветер?». Проверить, что каждый запрос показателей содержит новый настоящий погодный вызов, ответ совпадает с результатом, время и прогноз обозначены корректно. Затем новый чат → «Какая погода?» должен уточнить город; неоднозначный населённый пункт — регион. Для проверки недоступного сервера временно задать неслушающий адрес в `.env`, перезапустить и убедиться, что показывается ошибка без погодных чисел; вернуть исходный адрес.

## Ограничения и безопасность

- На стартовом экране нет кнопок фиксированных городов. Пользователь вводит произвольный город в поле чата; поддержка конкретного населённого пункта зависит от данных удалённого геопоиска.
- В браузере проверены стартовый экран без кнопок городов и реальный ответ для Мурманска с тремя вызовами: геопоиск кириллицей, геопоиск латиницей и погода по найденным координатам. Снимки: `diagnostics/no-city-buttons.jpg`, `diagnostics/murmansk-fixed.jpg`.
- Проверка Мурманска 22.11.2026 выявила особенность удалённого поиска: запрос «Мурманск» возвращал «Мурманский» и другие нерелевантные места, а `Murmansk` возвращал нужный город. Агент теперь проверяет совпадения названия и при неподходящей выдаче сам пробует другое написание через тот же MCP. Это общее правило, без списка исключений и без зашитых координат. Действительная неоднозначность по-прежнему требует уточнения региона. Доказательства: `diagnostics/geocoding-murmansk.json`, `diagnostics/murmansk-before.json`, `diagnostics/murmansk-after.json`. Повторный диалог получил текущую погоду и прогноз на завтра для подтверждённых MCP-координат Мурманска.

- Основной сквозной диалог с настоящим аккаунтом прошёл. Уточнение неоднозначных названий и все варианты исправления города требуют отдельных пользовательских сценариев; успешный основной тест не является исчерпывающей проверкой поведения LLM.
- Геопоиск Казани возвращает также одноимённые места в Кировской области. Агенту предписано уточнять регион при неоднозначности; можно сразу написать «Казань, Татарстан». В техническом тесте SDK явно проверяется Казань в Татарстане.
- Пакетные инструменты присутствуют на сервере, но модели в этой версии доступны одиночные: так проверяются происхождение координат и связь каждого вызова с городом. Дополнительные морские/архивные/воздушные инструменты обнаружены, но отдельно не принимаются и не проверены как функции продукта.
- Сервис округляет координаты до своей погодной сетки. В запрос уходят точные координаты MCP-геопоиска; координаты в погодном результате могут отличаться.
- Сервер не вернул поля единиц в проверенных ответах. Нормализация использует единицы реального запроса; при наличии единиц в результате они имеют приоритет.
- Финальный текст составляет LLM, поэтому его корректность требует сквозной проверки с выбранной моделью. Программно проверяются схемы, координаты, наличие данных, единицы, реальные журналы и пределы выполнения.
- `.env` игнорируется Git. Ключ читается только серверным кодом, клиент получает только флаг настройки. Секреты маскируются в выходных событиях; ошибки провайдера не пересылаются как есть.
- Браузер обращается к локальному API; внешних шрифтов, исполняемого HTML из ответов и прямых погодных API нет. React выводит ответы и JSON как текст. URL MCP берётся только из серверной настройки.
- Журналы содержат города и запросы, но не должны содержать секретов. Не вводите ключи и личные сведения в чат; используйте `.env` для настройки.
- Регистрация, БД, публичное размещение, голос и геолокация не реализуются, как и задано в ТЗ.

## Файлы

`server/agent.ts` — цикл выбора инструментов моделью; `server/mcp.ts` — официальный MCP-клиент, валидация и журнал; `server/weather.ts` — проверка данных и единиц; `server/index.ts` — локальный API и сессии; `src/main.tsx` — чат; `diagnostics/` — доказательства проверки. Lock-файл следует хранить вместе с исходниками и устанавливать через `npm ci`.

## Подготовка к публикации в GitHub

В репозиторий входят исходники, тесты, инструкции, `package.json`, `package-lock.json` и `.env.example` без настоящих ключей. Файлы `.env`, `.env.local` и другие `.env.*` (кроме шаблона), зависимости, сборка, журналы, локальная диагностика, кэши и временные файлы исключаются через `.gitignore`. Указанные выше отчёты и снимки в `diagnostics/` остаются на компьютере автора; живые проверки создают новые отчёты при запуске соответствующих команд.

Перед добавлением файлов проверьте состав будущего коммита:

```powershell
git status --short
git add --dry-run .
```

В списке должны отсутствовать `.env`, `node_modules`, `dist` и `diagnostics`. `.env.example` должен присутствовать и содержать только пустые значения ключей и общие настройки. Не используйте `git add -f` для файлов с секретами. `.gitignore` не удаляет уже отслеживаемые файлы из истории: если ключ был опубликован, его необходимо отозвать у провайдера и отдельно очистить историю.

Для запуска скачанной копии проекта используйте `npm ci`, создайте свой `.env` по шаблону и выполните `npm run dev`. Ключ OpenAI каждый участник занятия настраивает локально.
